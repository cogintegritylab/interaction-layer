# Interaction Layer Protocol — Specification

**Version: interaction-layer/v2 (draft, 2026-05)**
**Issuer of reference implementation: [Cognitive Integrity Lab](https://sites.temple.edu/cilab/)**

This document specifies the data formats, canonicalization rules, signing
process, and verification semantics of the interaction-layer protocol. It is
intended to be sufficient for an independent implementer to build a verifier
or a compatible issuer.

The protocol is intentionally simple. Trust derives from openness, public
verification, and mathematics.

**Implementation status.** This document specifies the full v2 protocol.
The deployed reference implementation supports v1 finalize-only receipts;
the v2 checkpoint endpoint and `.cogdoc` flow are landing in stages. See
[README](README.md) for current milestone status.

## 1. Scope

- Define a portable file format (`.cogdoc`) that holds a piece of writing
  together with a tamper-evident, server-signed history of checkpoints.
- Define the schema, canonicalization, and signing rules that make
  verification reproducible across implementations.
- Define the minimum security posture for the signing endpoint such that
  trivial abuse (e.g., one-line curl) is blocked without surveilling users
  or interrupting legitimate writing.
- This protocol does **not** prove human authorship. It produces a
  cryptographically signed receipt binding the editor mode, the text, and
  the time of signing. The signed bundle is tamper-evident and publicly
  verifiable.
- This protocol does **not** detect AI-generated content. There is no
  classifier; the protocol does not inspect prose.
- This protocol does **not** require any cross-device synchronization
  infrastructure on the server side. Portability across devices is
  achieved through the user moving the `.cogdoc` file (e.g., via iCloud
  Drive).
- This protocol minimizes server-side storage. Writing content is never
  stored. Checkpoint signing is stateless: the server signs hashes and
  returns; nothing about the request is persisted. The only data that
  persists server-side is a small hash-only record behind each v1
  finalize verify URL.

## 2. Core concepts

A **document** is a piece of writing with a stable identity, accumulating
revisions over time. Documents are identified by a `doc_id`, generated by
the client when the document is first created.

A **checkpoint** is a snapshot of a document's text at a particular moment,
signed by an issuer's private key. Each checkpoint references the previous
checkpoint by hash, forming a hash chain.

A **`.cogdoc` file** is a plain-text JSON file containing the current text
of a document and the full chain of signed checkpoints made so far. It is
the unit of portability between devices.

An **issuer** is the entity whose private key signs checkpoints. The
reference implementation's issuer is the Cognitive Integrity Lab. The
protocol is multi-issuer: any party can run an issuer for their domain.

A **verifier** is software (a website, an app, a command-line tool) that
reads a `.cogdoc` and confirms the chain's signatures match the public key
declared in each checkpoint.

## 3. The `.cogdoc` file format

A `.cogdoc` file is UTF-8 JSON. Its top-level structure:

```json
{
  "format_version": 2,
  "doc_id": "k3pT2nQ8vL5xR1aZ",
  "mode": "ai_free",
  "content": "the full text of the document",
  "checkpoints": [
    {
      "payload": { ... },
      "signature": "...",
      "kid": "cil-v1"
    }
  ],
  "final_receipt": null
}
```

### Field definitions

- **`format_version`** (integer, required): currently `2`. A reader MUST
  reject files with unknown future versions.
- **`doc_id`** (string, required): a base64url-encoded 12-byte random
  identifier (16 characters). Generated by the client when the document is
  first created. Stable across the document's lifetime.
- **`mode`** (string, required): the protocol mode the writer is claiming.
  For v2, the canonical values are:
  - `ai_free` — composed by hand in a paste-blocked editor
  - `cognitive_authorship_check` (reserved, see CIL roadmap)
  - `socratic_mode` (reserved)
  - Issuers may extend with custom mode strings.
- **`content`** (string, required): the current text of the document. May
  be modified outside the editor; the chain will detect this on verification.
- **`checkpoints`** (array, required, may be empty): an ordered list of
  signed checkpoint objects (defined in §4). The empty array represents an
  uncertified draft.
- **`final_receipt`** (object or null, required): if non-null, contains a
  signed final receipt. When set, the document is considered "published"
  and the final receipt's verify URL is shareable. Schema is identical to a
  checkpoint object except its payload has `"type": "final"`.

## 4. The checkpoint payload

Each checkpoint object contains a payload, a signature over the canonical
form of that payload, and a key identifier:

```json
{
  "payload": {
    "v": "interaction-layer/v2",
    "type": "checkpoint",
    "doc_id": "k3pT2nQ8vL5xR1aZ",
    "mode": "ai_free",
    "hash_algorithm": "sha-256",
    "canonical_text_v": 1,
    "text_hash": "abc123...",
    "prev_checkpoint_hash": "def456...",
    "issued_at": "2026-05-15T14:23:01.842Z",
    "issuer": "Cognitive Integrity Lab"
  },
  "signature": "<base64 Ed25519 signature>",
  "kid": "cil-v1"
}
```

### Payload field definitions

All payload fields are required.

- **`v`** (string): protocol version, exactly `"interaction-layer/v2"`.
- **`type`** (string): one of:
  - `"checkpoint"` — an intermediate save during composition.
  - `"final"` — a published, shareable final state (used in
    `final_receipt`, not in the `checkpoints` array).
- **`doc_id`** (string): same as `.cogdoc.doc_id`. Binds the checkpoint
  to a particular document.
- **`mode`** (string): same as `.cogdoc.mode`.
- **`hash_algorithm`** (string): `"sha-256"`. Specified for forward
  compatibility.
- **`canonical_text_v`** (integer): version of the canonical-text algorithm
  used (§5.1). Currently `1`.
- **`text_hash`** (string): hex-encoded SHA-256 of the canonical text
  (§6).
- **`prev_checkpoint_hash`** (string): hex-encoded SHA-256 of the previous
  checkpoint's canonical payload bytes. For the first checkpoint in a
  document, this is the literal string `"genesis"`.
- **`issued_at`** (string): ISO 8601 timestamp with millisecond precision
  and `Z` suffix (UTC).
- **`issuer`** (string): the issuer's human-readable label.

### Outer object field definitions

- **`payload`**: the object above.
- **`signature`**: a base64-encoded Ed25519 signature over the canonical
  payload bytes (§5.2). 64 bytes of signature, ≈88 characters of base64.
- **`kid`** (string): key identifier, e.g., `"cil-v1"`. Allows future key
  rotation while maintaining backward-verifiable receipts.

## 5. Canonicalization

To produce deterministic bytes for hashing and signing, both text and
payload JSON are canonicalized. Implementations MUST produce byte-identical
canonical forms; a one-byte difference invalidates a signature.

### 5.1 Canonical text (`canonical_text_v: 1`)

The transformation, applied in order:

1. Replace all `CR LF` (U+000D U+000A) and bare `CR` (U+000D) with `LF` (U+000A).
2. For each line, strip trailing spaces (U+0020) and tabs (U+0009).
3. Collapse any run of three or more consecutive `LF` characters to exactly
   two `LF` characters.
4. Strip leading and trailing whitespace from the entire string
   (whitespace = space, tab, LF).
5. The result is UTF-8 encoded for hashing.

No Unicode normalization (NFC/NFD), no case folding, no quote
substitution. Meaningful character differences (e.g., curly quotes vs.
straight) must be preserved as they appear.

### 5.2 Canonical payload JSON

To produce a canonical byte-string from a checkpoint payload:

1. Take the payload object's keys.
2. Sort keys in ascending lexicographic byte order (UTF-8 codepoint sort).
3. Re-serialize as JSON with:
   - No whitespace between tokens.
   - Standard JSON string escaping (RFC 8259).
   - Numbers in decimal form (no exponent notation).
   - All field values must be strings or integers; no floats, no nested
     objects, no nulls in the payload.

The resulting byte-string is what gets signed. Implementations SHOULD
compute this on a freshly-cloned object to avoid mutating shared state.

## 6. Hashing

All hashes in this protocol are SHA-256, output as **lowercase hexadecimal
strings** (64 characters).

- **Text hash**: SHA-256 of the canonical-text UTF-8 bytes (§5.1), hex.
- **Previous-checkpoint hash**: SHA-256 of the previous checkpoint's
  canonical payload JSON bytes (§5.2), hex.

## 7. Signing

Signatures are **Ed25519**, computed over the canonical payload bytes
(§5.2). The signature is base64-encoded (standard alphabet, with padding).

Each issuer maintains an Ed25519 keypair. The private key is held only by
the issuer's signing server and used only by the signing endpoint (§8).
The public key is published alongside the issuer's identity — for example,
on a public page at the issuer's domain, and committed to source control.

The reference issuer's public key is published at
`https://interaction.cognitio.fyi/about` and in the `lib/public-key.ts`
file of the open-source repository.

## 8. The signing endpoint

The reference issuer exposes a single endpoint for issuing signed
checkpoints.

### Request

`POST /api/checkpoint`

**Required headers:**
- `Cookie: <session-cookie>` (HTTP-only session cookie issued on
  composition-page load)
- `X-CSRF-Token: <token>` (CSRF token issued with the composition page)
- `Origin: https://interaction.cognitio.fyi` (or the issuer's deployed
  origin)

**Required body** (JSON):

```json
{
  "doc_id": "k3pT2nQ8vL5xR1aZ",
  "mode": "ai_free",
  "text_hash": "abc123...",
  "prev_checkpoint_hash": "def456..."
}
```

The client supplies the doc_id, mode, hash of the canonical text, and the
previous checkpoint hash (or `"genesis"`). The server fills in everything
else (`v`, `type`, `hash_algorithm`, `canonical_text_v`, `issued_at`,
`issuer`) and signs.

### Response

```json
{
  "payload": { ... full payload as in §4 ... },
  "signature": "<base64>",
  "kid": "cil-v1"
}
```

The client stores the entire response object as the next entry in the
`.cogdoc.checkpoints` array.

### Security posture

This is the minimum posture, designed to be unobtrusive:

- **Session cookie + CSRF token**: prevents trivial curl exploits.
  Endpoint rejects requests without both.
- **Origin check**: requests must originate from the issuer's deployed
  domain.
- **Per-session rate limit**: a generous limit (e.g., 200 signing
  requests per session per hour). Designed so a real user saving every 30
  seconds for an hour stays well under. Industrial abuse hits the limit
  quickly.
- **No tracking of user behavior**. Standard HTTP access logs only (path,
  status, IP, timestamp). No per-session behavioral analysis, no anomaly
  scoring, no fingerprinting.
- **Fail open for legitimate users**. If the server is uncertain (e.g.,
  rate-limit edge case), prefer to sign rather than block. A user who
  loses work due to security plumbing is a far worse failure than an
  attacker who succeeds.

A determined attacker who scripts the full session bootstrap (load
composition page, extract cookie and CSRF token, issue checkpoint
requests) can still mint signatures. That is acknowledged. Defense
beyond this is honest framing in user-facing copy (see §13).

### Error responses

| Status | Meaning |
| --- | --- |
| `400` | Malformed body |
| `403` | Missing or invalid session/CSRF/Origin |
| `429` | Rate limit exceeded; includes `Retry-After` header |
| `500` | Server error (transient; client may retry) |

The endpoint MUST NOT log request bodies or hashes beyond what is needed
for the immediate signing operation.

## 9. Verification

Given a `.cogdoc` file and the issuer's public key, a verifier performs
these checks:

1. **Format check**. Reject if `format_version` is unknown.
2. **Chain check**. For each checkpoint in `checkpoints`, in order:
   - Verify `payload.prev_checkpoint_hash` equals SHA-256 of the previous
     checkpoint's canonical payload bytes (or equals `"genesis"` for the
     first checkpoint).
   - Verify `payload.doc_id` equals `.cogdoc.doc_id`.
   - Verify `signature` is a valid Ed25519 signature over the canonical
     payload bytes, using the public key for `kid`.
3. **Final receipt check** (if `final_receipt` is non-null):
   - Same chain check as above; `prev_checkpoint_hash` must equal the
     last checkpoint in the array (or `"genesis"` if the array is empty).
   - Verify signature.
4. **Current text check**. Compute SHA-256 of the canonical form of
   `.cogdoc.content` (§5.1, §6).
   - If `final_receipt` is non-null, compare to
     `final_receipt.payload.text_hash`.
   - Otherwise, if checkpoints is non-empty, compare to the last
     checkpoint's `text_hash`.
   - Otherwise, no check (no checkpoints yet).

Based on the outcome, the verifier reports one of three UI states (§10).

## 10. UI states

A `.cogdoc` opened in a verifier-aware application is in exactly one of:

- **`NO_CHECKPOINT_YET`**: `checkpoints` array is empty and
  `final_receipt` is null. The document has no certification. The editor
  may open and edit it freely.
- **`VALID_CERTIFIED`**: chain checks pass AND current text hash matches
  the last checkpoint's (or final receipt's) text hash. The document is
  in certified state.
- **`CERTIFICATION_BROKEN`**: chain checks pass for prior signatures, but
  the current text hash does NOT match the last checkpoint. The text has
  been modified outside the editor since the last certification. The
  editor MUST display the broken state prominently and MUST disable any
  in-place re-certification (Save and Finalize). To regain a certified
  state, the user must clear the editor and re-enter the content through
  the normal paste-blocked composition flow, which produces a fresh
  `doc_id` and a new chain. The broken file is preserved for the user's
  reference.

Implementations MAY add transition states (e.g., "editing,
certification-pending-on-save") but these MUST NOT be reported as
verification outcomes.

## 11. Relationship to v1 (finalize-only) receipts

The reference implementation's v1 (already deployed) consists of
server-stored finalize records with verify URLs of the form
`/verify/<id>`, where the receipt is fetched from a database row. The v1
receipt structure was:

```json
{
  "protocol": "interaction-layer/v1",
  "mode": "ai_free",
  "hash_algorithm": "sha-256",
  "hash": "...",
  "issued_at": "...",
  "issuer": "Cognitive Integrity Lab",
  "key_id": "cil-v1"
}
```

v1 receipts remain verifiable indefinitely against the same public key
(`cil-v1`). The v2 protocol is additive: it introduces the checkpoint
chain and the `.cogdoc` file, but does not invalidate v1 receipts.

A v2 document MAY produce a v1-style verify URL when finalized, by
storing only the final receipt server-side. The relationship between v1
verify URLs and v2 `.cogdoc` files is:

- **Email/short-message workflow**: writer composes, finalizes, gets a
  short verify URL pointing to a server-stored final receipt. No
  `.cogdoc` exchanged. Recipient pastes text on the verify page.
- **Long-form workflow**: writer uses `.cogdoc` for the writing process.
  On finalize, the final receipt is recorded both inside the `.cogdoc`
  and (optionally) on the server, yielding a verify URL. Recipient may
  use either path.

## 12. Versioning and key rotation

### Protocol version

The protocol version string (`v` field) is `interaction-layer/v2` in this
document. Future versions may add fields. Verifiers MUST reject payloads
whose `v` is unknown.

A breaking format change (e.g., changing canonicalization rules)
increments the major version (`v3`, `v4`, …). New checkpoints SHOULD use
the latest version; existing receipts MUST remain verifiable against
their stated version.

### Canonical-text algorithm version

The `canonical_text_v` field tracks the version of the canonical-text
function (§5.1). A change here (even a clarification) MUST bump this
integer. Verifiers MUST apply the algorithm matching the
`canonical_text_v` in the payload.

### Key rotation

Each issuer publishes a list of currently-valid public keys, each with a
`kid`. New checkpoints SHOULD use the issuer's current key. Old
checkpoints remain verifiable against their original `kid` as long as the
issuer publishes the corresponding public key.

The reference issuer's current and historical public keys are listed at
`https://interaction.cognitio.fyi/about` and in
`lib/public-key.ts` in the open-source repository.

A compromised private key MUST trigger a key rotation: the compromised
`kid` is marked as compromised in the issuer's published key list, and
new checkpoints use a fresh key. Receipts signed by the compromised key
SHOULD be displayed by verifiers with a warning indicator.

## 13. What this protocol proves (and does not)

The protocol binds an editor mode, a text fingerprint, and a timestamp
under a cryptographic signature, with chained checkpoints that detect
tampering after the fact. It does not verify the lived composition event
unless a stronger client or issuer assurance layer (see §14) is added.

### What is proved

Given a `.cogdoc` in `VALID_CERTIFIED` state:

- The text in the file matches, after canonicalization, the text whose
  hash is in the last checkpoint's payload (proven by §6).
- That last checkpoint's payload was signed by the holder of the private
  key corresponding to `kid` (proven by Ed25519 signature verification).
- The chain of preceding checkpoints is internally consistent: each
  prev_checkpoint_hash matches the actual prior payload (proven by §9).
- The timestamps in the chain are claimed by the issuer; if those claims
  are credible, the writer engaged in a sequence of save events at those
  times.

### What is not proved

- That the writer composed the text without consulting AI, dictation,
  or other external sources. No automated tool — not even a
  hypothetically perfect AI detector — can verify what a writer was
  reading or thinking during composition. The protocol takes a first
  step in that direction with a tamper-evident cryptographic record of
  the editor mode, the text, and the time of signing.
- That the timestamps are genuinely contemporaneous and not backdated
  by the issuer (this requires an independent timestamping service such
  as OpenTimestamps; not specified in this version).
- That the code running on the issuer's server matches the issuer's
  published source code (this requires reproducible builds with
  cryptographic attestations; not specified in this version).

The protocol certifies *the editor mode, the text, and the time of
signing*, not authorship in any deep sense. Implementations and
user-facing copy MUST not overclaim. See
[/about](https://interaction.cognitio.fyi/about) for the user-facing
version of these limits, and §14 for the assurance-level framework that
locates the current implementation in a broader trust landscape.

## 14. Assurance levels

The interaction-layer protocol can be implemented at multiple assurance
levels, depending on which components have been hardened and audited.
**The current reference implementation operates at L1**: it uses browser
and server safeguards (HTTP-only session cookies, CSRF tokens, origin
checks, generous rate limiting, open-source code, public verification
keys) but should not be treated as a high-stakes authorship guarantee.
Higher-assurance versions will require reproducible builds with
attestation (L2), verified clients (L3), and institutional deployment
with independent audit (L4). **This is a research prototype, not yet a
high-assurance certification system.**

The levels are additive: a system operating at L3 also satisfies L1
and L2.

### L0 — Honor system

A claim of process with no cryptography. Email-signature boilerplate,
plain disclaimers. No tamper-evidence. Included for comparison only.

### L1 — Cryptographic seal *(current reference implementation)*

- Open-source code; publicly published verification keys.
- Signing endpoint protected by HTTP-only session cookie, CSRF token,
  origin check, and per-session rate limit.
- Tamper-evidence after signing is mathematically guaranteed: integrity
  of text and timestamps cannot be silently violated.
- Endpoint can still be abused by a moderately-skilled scripter who
  simulates a full session lifecycle. Defense beyond this is honest
  framing in user-facing copy, not technical hardening.
- Adequate for collegial and educational use among good-faith parties.

### L2 — Verifiable code-to-deploy chain

L1 plus:

- Reproducible builds with cryptographic attestation (e.g., SLSA Level 3+
  provenance). The binary running on the signing server is mathematically
  provable to be built from a specific public source commit. The "is this
  really the code?" gap (currently relying on the hosting provider as a
  trusted intermediary) is closed.
- Independent timestamping anchored to a public append-only ledger
  (e.g., OpenTimestamps anchoring to Bitcoin). The issuer cannot
  credibly backdate.

Adequate for contexts where the issuer might be incentivized to
manipulate timestamps or quietly modify the deployed code.

### L3 — Verified client

L2 plus:

- The composition application itself proves its integrity to the
  signing server (signed binary, attested webview, or analogous
  mechanism). Closes the "modified frontend" gap: an adversary can no
  longer feed arbitrary hashes through a tampered editor and still
  receive valid signatures.
- Implementation must preserve open-source auditability and user
  agency. Browser-vendor attestation schemes (e.g., Web Environment
  Integrity) that centralize power are explicitly NOT compatible with
  this protocol's philosophy. Acceptable paths include signed open-source
  native clients, signed browser extensions with auditable manifests,
  and client-side voluntary evidence cooperatively interpreted by the
  server.

Adequate where the conditions of composition must be cryptographically
enforced, not merely declared.

### L4 — Institutional deployment and audit

L3 plus:

- Issuer is an accountable institution (university, journal, court,
  professional body) with formal procedures for key management,
  incident response, and key rotation, published openly.
- Independent third-party security audit, published, repeated on a
  defined schedule.
- Public registry of issuers and their audit history.
- Documented procedures for revoking compromised keys and for
  marking historical receipts signed by a compromised key.

Adequate for high-stakes settings: legal admissibility, academic
integrity adjudication, professional certifications, regulated
industries.

### Current state and roadmap

- **L1**: in production at `interaction.cognitio.fyi`.
- **L2**: in active development. The Vercel-recorded GitHub commit
  chain already provides an *informal* version of code-to-deploy
  traceability; cryptographic attestation (SLSA provenance) and public
  timestamping (OpenTimestamps) are the next concrete steps.
- **L3**: research and design phase. Implementation options under
  evaluation; chosen path will be documented as part of the v3 protocol
  revision.
- **L4**: depends on adoption by accountable institutions. Cognitive
  Integrity Lab can offer this for its own deployments as the protocol
  matures and institutional partners onboard.

A verifier MAY display the assurance level claimed by the issuer of a
given receipt, along with any independent audit status. User-facing copy
SHOULD make the relevant level visible to the reader rather than
implying a uniformly high level of assurance.

## 15. Reference implementation notes

The reference implementation is at
[github.com/cogintegritylab/interaction-layer](https://github.com/cogintegritylab/interaction-layer).
Notes for implementers reading the reference code:

- **Canonical text** is implemented in `lib/canonical.ts`. Any change
  there must bump `canonical_text_v`.
- **Canonical JSON** is also in `lib/canonical.ts`.
- **Signing** uses Node's built-in `crypto.subtle` with Ed25519.
- **Public key** is in `lib/public-key.ts` (committed in cleartext;
  meant to be public).
- **Private key** is a Vercel environment variable, never committed.
- **The composition page** at `/` is a paste-blocked editor.
- **The verify page** at `/verify/[id]` is the v1 verify path; the v2
  verifier (for `.cogdoc` files) is an opening flow on `/` itself,
  triggered by an "Open Draft" control.

The reference implementation's `.cogdoc` flow (Phase 2a) adds:

- `POST /api/checkpoint` — the signing endpoint described in §8.
- "Save for Later" — a button on the composition page that triggers a
  checkpoint request, embeds the response in a `.cogdoc`, and saves the
  file via browser download.
- "Open Draft" — a button on the composition page that loads a `.cogdoc`
  via file picker, runs verification (§9), populates the editor with
  `content`, and displays the UI state (§10).
